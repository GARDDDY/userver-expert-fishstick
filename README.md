# Куда уходит время сборки userver-сервиса

## Запуск

```bash
./run.sh [runs]    # по умолчанию 5
```

## Окружение

- Intel Core i7-11700F, 2.5 GHz
- Windows 11, WSL2 Docker Desktop

## Измерение

Сначала один запуск для сохранения файлов в кэш, чтобы время на считывание с диска не учитывалось

Дальше 5 запусков. В каждом все варианты собираются с нуля. Чтобы результат не зависел от порядка, варианты чередуются.

В каждом запуске измеряется время `cmake --build` (wall-time)

| Вариант | Что это |
|---|---|
| `baseline` | С `-ftime-trace`, без прекомпиляции заголовков |
| `baseline_notrace` | Без `-ftime-trace` |
| `pch_onetarg` | У каждой цели своя прекомпиляция |
| `pch_general` | Строится одна общая прекомпиляция |

Сама `-ftime-trace` почти не влияет на сборку: 14.1 секунд без нее; 14.6 &mdash; с ней

## Результаты

Все складывается в `./results/` и **перезаписывается** при каждом запуске

**Сырой вывод Clang Build Analyzer** в `results/<вариант>/cba_report_N.txt`

- `summary.md` &mdash; итоговая таблица по всем вариантам
- `environment.txt` &mdash; железо тестера и версии инструментов
- `<вариант>/` &mdash; по папке на каждый вариант сборки, в ней `N` &mdash; номер запуска:
  - `cba_report_N.txt` &mdash; сырой отчет Clang Build Analyzer
  - `wall_N.txt` &mdash; сколько секунд длилась сборка
  - `ninja_log_N.txt` &mdash; сколько длился каждый шаг сборки
  - `build_N.log` &mdash; вывод самой сборки
  - `configure_N.log` &mdash; вывод cmake перед сборкой
  - `*_warmup.log` &mdash; то же для прогревочного запуска

## Выводы

Опорная сборка &mdash; `baseline`. Выводы по 3 запуску (его время 14.6 равно медиане)

1. **Больше всего времени уходит на разбор заголовков, а не на генерацию кода.** 
Clang Build Analyzer показал, что разбор фронтенда занял 26.6 с, а генерация и оптимизация кода бэкенда &mdash; 6.3 секунды. 81% и 19%

2. **Одни и те же тяжелые заголовки разбираются заново в каждом .cpp.** 
`hello_service.usrv.pb.hpp` подключается 3 раза и занимает 4.4 секунд, `hello.pb.h` &mdash; 6 раз и 2.2 секунд, `userver/components/component.hpp` &mdash; 4 и 2.7, `fmt/format.h` &mdash; 10 и 1.8

3. **Сгенерированный gRPC-код и `main.cpp` &mdash; самые дорогие.**
2 файла `*.usrv.pb.cpp` занимают по 5.0 секунд. 4 .cpp, сгенерированных из proto, берут 14.4 из 32.9 секунд (44%) всей компиляции. `main.cpp` &mdash; еще 5.7 секунд (17%)

4. **Линковка в Clang Build Analyzer не видна, но съедает хвост сборки.** 
Компиляция заканчивается на 10.8 секунде, а готовый `bench_service` появляется на 14.6, то есть больше четверти времени (26%) &mdash; это линковка

## Гипотеза и проверка

**Гипотеза:** 81% времени занимает frontend, а тяжелые userver-заголовки повторяются во всех TU. Тогда общая прекомпиляция заголовков (`pch_general`) сократит время сборки

В прекомпиляцию вошли `component.hpp`, `http_handler_base.hpp`, `postgres/mongo/component.hpp`, `postgres/mongo/cluster.hpp`, `postgres/mongo/pool.hpp`, `ugrpc/service_component_base.hpp`,`ugrpc/client_factory_component.hpp`

В `pch_general` на самом деле два PCH: общий и маленький для proto-цели (она не видит include-пути mongo).

| Вариант | Медиана wall (и min-max), сек | Разница со временем baseline, % | Analyzer - frontend, сек | Analyzer - backend, сек | Шаги компиляции |
|---|---|---|---|---|---|
| baseline | 14.6 (13.3-15.7) | 0 | 26.9 | 6.6 | 12 |
| pch_onetarg | 17.6 (16.9-23.0) | +21 | 27.5 | 7.7 | 17 |
| pch_general | 14.0 (12.5-17.1) | -4 | 13.9 | 8.4 | 14 |

**Результат: гипотеза не подтвердилась**

- `pch_general` по медиане быстрее baseline: 14.0 против 14.6 секунд (-4%), но быстрее не всегда. 
Разница по запускам (baseline - pch_general): -3.8, -1.2, 2.0, 0.6, 2.8 секунд. Быстрее он в 3 запусках из 5, в двух медленнее, а в среднем одинаково (14.6 и 14.7)

- Разбор заголовков frontend упал почти вдвое: вместо 26.9 стало 13.9. Но генерация кода стала дольше: вместо 6.6 стало 8.4. Суммарное время компиляции по ninja упало с 38.0 до 26.1 секунд, а время сборки почти не изменилось

- По `.ninja_log` (все для того же 3 запуска): сначала нужно сделать 2 прекомпиляции (2.6 для proto и 4.3 для основной цели), и пока они не готовы, остальные .cpp этих целей ждут. А линковка (4.0 из 12.5 секунд) от прекомпиляции не зависит. Поэтому экономия работы почти не превращается в экономию времени сборки

- `pch_onetarg` медленнее baseline во всех 5 запусках: 17.6 против 14.6 секунд (+21%)

## Возникшие проблемы

- При запуске на очень загруженной машине выигрывал `pch_general`. Он был быстрее `baseline` в каждом из 5 запусков на 7%. Сырые данные того запуска я сохранял, но факт остается фактом

- Общая прекомпиляция немного не общая. gRPC не видит заголовки mongo (ошибка `bson/bson.h not found`). Поэтому для него происходит отдельная маленькая прекомпиляция, и в `pch_general` их две, а не одна как должна быть по названию
